# LCD failure — 2026-09-13

> **Historical.** This incident concerns the pre-reinstall setup: a patched
> coolercontrold and a liquidctl driver in `/usr/local`. Neither exists any
> more, and the LCD now runs through `cc-plugin-zalman-lcd` (see
> [WORKLOG-2026-10-09.md](WORKLOG-2026-10-09.md)). The driver fix described
> below lives on in `zalman_lcd/device.py` and is still in use.

## Symptom

CoolerDash was running and producing PNGs, but LCD uploads ended with HTTP 500.
CoolerControl's internal liquidctl bridge reported the underlying error:

```text
502 Bad Gateway
Matching LCD serial port not found; cdc_acm must own the device
```

## Diagnosis

The hardware had not disappeared:

```text
Bus 001 Device 008: ID 0483:5740 STMicroelectronics Virtual COM Port
/dev/ttyACM0 -> cdc_acm
/dev/serial/by-id/usb-HWCX-TECH_USB_Display-if00 -> ../../ttyACM0
```

The kernel log showed that the device connected at boot with USB address 5. At
13:33 it dropped and re-enumerated with address 8. CoolerControl had started at
12:32, so its liquidctl object still held the old identity `bus=usb1,address=5`.
`zalman_lcd.device.find_tty()` matched only on that ephemeral address and therefore
rejected `/dev/ttyACM0`, even though the port still existed.

So the failure was not a `cdc_acm` loading or permission problem. The matching
logic did not handle the USB address changing on reconnect.

## Permanent fix

`zalman-Alpha2-DS-LCD-Linux/zalman_lcd/device.py` was changed:

1. First look for an exact bus/address match.
2. If the old address no longer exists and exactly one Zalman serial port with
   VID/PID `0483:5740` is present, fall back to that port.
3. If several Zalman displays are present, do not pick an ambiguous port.

A regression test for the address 5 → 8 scenario was added to
`tests/test_client.py`. Result: **9/9 passed**.

The changed file was installed to:

```text
/usr/local/lib/zalman-integration/zalman_lcd/device.py
```

The SHA-256 of the source and the installed file matched at verification time:

```text
67c7a266e4b412ca81a4e4714a6006c89e90f0645b7ff42bcab3c80407e28a40
```

`coolercontrold.service` was then restarted, and the dependent CoolerDash plugin
restarted with it.

## Verification evidence

As of 2026-09-13 16:22:16 the journal showed:

```text
Zalman LCD connected through /dev/ttyACM0 (cdc_acm)
Zalman LCD overlay updated
"PUT /devices/1/screen HTTP/1.1" 200
```

Many further updates over about 35 seconds also returned HTTP 200, and neither
`502 Bad Gateway` nor `Matching LCD` reappeared. The generated
`/var/lib/coolercontrol/plugins/coolerdash/coolerdash.png` kept being updated.

The transient hidraw and RDNA fan-curve warnings seen at startup were unrelated
to the LCD failure.

## Rollback (at the time)

Revert the change in the source branch, install the previous `device.py` into
`/usr/local/lib/zalman-integration/zalman_lcd/`, and restart CoolerControl.
`scripts/install-zalman-fix.sh` reinstalled the fix.
